# Contributing

This page covers how to write and contribute code for Project Comet. Project setup instructions are in the [README](README.md).

## Before you start

- For non maintainers, open an issue first and say what you plan to do. A change a maintainer hasn't agreed to probably will not be merged.
- Creative work is made by people: models, textures, art, audio, level design and in-game text. Don't contribute any of it generated by AI.
- AI tools are fine for code, but you are responsible for any code you submit, so make sure you understand it.

## Writing code

The project includes tools to check and fix code style, so it doesn't need to be done manually. You should run the checks yourself before submission.

- **CSharpier** formats all C# and the project files. Run it with `dotnet csharpier format .`.
- **Analyzers** run in every build, and errors cause the build to fail.
- **`tools/run check`** runs the same checks as GitHub Actions: a formatting check, a build of the content files, and the unit tests.

The rest of the rules are not covered by the automated checks, but try to follow them.

- **Write it once.** If the same logic would appear in two places, share it.
- **Check input where it enters** (players, network, files, config), then trust the code's own calls.
- **Keep comments rare.** Only when a reader would get the code wrong without one, and say why. Comet's public API keeps short `<summary>` comments that add something, such as units.
- **Clean up after yourself.** Delete code your change leaves unused, and fix comments it makes wrong or leaves above the wrong code.
- **Keep refactors separate.** A cleanup does exactly what the old code did; behavior changes go in their own commit.
- **Keep files a readable size.** Split a file along a clear line when it gets too big to follow.
- **Tests** check behavior through the public API surface, stay short with shared helpers.
- **Interface text** lives in `shapeland/content/strings/`.

## Pull requests

Pull requests are squash-merged into `main`, so the title and description become the commit message. Keep them short: what changed and why. Put the main code first, then its tests, then mechanical changes, and end the description with a note on which files to read closely.

1. Branch off an up-to-date `main`. If you are not a maintainer, fork the repo first and add the branch in your fork.
2. Run `tools/run check` before pushing. CI runs on every push, but will do so in a fork only if you turn on GitHub Actions there. If you changed Unity code, also run `tools/run unity-batch test PlayMode`. The CI doesn't run Unity yet, so this is critical.
3. Open the pull request against `main`. From a fork, leave "Allow edits by maintainers" on.
4. A maintainer reviews and then merges it if it passes. Push any requested changes to the same branch.
